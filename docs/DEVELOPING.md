# Developing CatalyX

## Requirements

- Windows 10/11 (the program uses Win32 throughout; it does not build elsewhere).
- A recent stable Rust toolchain with the `x86_64-pc-windows-msvc` target (Visual Studio Build Tools).
- Optional: an NVIDIA card to exercise the graphics features; administrator rights for the features that need
  them.

## Two programs, three packages

One workspace, and the window is a skin over the core. `crates/catalyx-core/` is the program: everything except
drawing (it links no egui). `app/src/main.rs` is a Windows *window* program (no console, so starting it never
opens a terminal; typed in a terminal with a command it joins that terminal and prints there) and its one skin
line calls `skins/classic/`. `catalyx-cli.exe` (`crates/catalyx-core/src/bin/catalyx-cli.rs`) is the same core
as a *console* program: use it in scripts, pipes and CI, because a shell waits for it and exit codes, redirects
and Ctrl+C behave. All three are built by `cargo build --release --workspace`.
Start-up timing: set `CATALYX_TRACE=1` and read `%TEMP%\catalyx-startup.txt`.

## Build and check

```powershell
cargo build --release            # target\release\catalyx.exe
cargo test --release             # unit tests (no Windows state is changed)
cargo clippy --release           # must be clean: CI runs it with -D warnings
cargo fmt --check                # rustfmt.toml: max_width 140, Unix newlines
```

The tests cover what needs no Windows state: the config and its version gate, the settings catalogue, intents
(including stale ids), the tagged activity log, the status cell's "notify once per change" rule, and the
snapshot sharing contract - `procs::latest` hands out the same `Arc<Snapshot>`, never a copy, and a reader's
sample cannot change under it.

Text that people or scripts read is pinned whole, not by keywords: `src/cli/help.txt` and
`src/cli/show-balanced.txt` are compared byte for byte by tests. They are generated by the program itself
(`catalyx-cli help`, `catalyx-cli show Balanced` against an empty `CATALYX_DATA`); a deliberate change to
that text means regenerating the file in the same commit. A failing test prints the new text.

Close CatalyX before building (Windows locks the running exe) and do not run two builds at once.

## The built-in checks (they drive the real window)

All of them use a scratch data folder and end by themselves under a 110-second watchdog. None touches your
real config, journal or games.

```powershell
# End-to-end: starts a stand-in "game" (a renamed copy of ping.exe), boosts it, checks its priority and the
# live HUD, restores, and writes a JSON report. Takes about 10 seconds.
.\target\release\catalyx.exe --self-test shots\selftest.json --no-elevate

# A screenshot of any page, with demo data
.\target\release\catalyx.exe --screenshot shots\boost.png --tab boost --size 1180x760 --no-elevate
.\target\release\catalyx.exe --screenshot shots\live.png  --tab boost --demo-session --accent ember --appearance dark --no-elevate

# Every page
.\target\release\catalyx.exe --tour shots\tour --no-elevate

# Does each boost feature really work on THIS PC? (changes and restores real settings, briefly)
.\target\release\catalyx.exe doctor --gpu
```

Pass a path without spaces to `Start-Process -ArgumentList` (or quote it), or the arguments split.
`--tab` takes `boost`, `games`, `apps`, `services`, `profiles`, `tuning`, `settings`.

## Testing against Windows safely

- **Never run a real game or a launcher with an anti-cheat driver** in a test. Use a stand-in: copy
  `%SystemRoot%\System32\PING.EXE` to a folder *outside* Windows and rename it (the program never takes
  programs from the Windows folder for a game).
- Point everything at a scratch folder: `$env:CATALYX_DATA = "$env:TEMP\cx-test"`. Remove it afterwards.
- `catalyx play <game> --dry-run` and `catalyx boost --dry-run` show the plan and change nothing.
- The quiet desktop switches your taskbar off for a few seconds: `catalyx desktop test 6`. If anything goes
  wrong, `catalyx desktop restore` (or Task Manager > Run new task > `explorer.exe`).
- Tests and checks must never hang: give every wait a time limit.

## Tooling (scripts/)

Everything repetitive is a script. They are plain PowerShell, take `-?`/`Get-Help` for details, never touch your
real settings (they use scratch data) and exit non-zero on failure.

| Script | What it does |
|---|---|
| `scripts\check.ps1` | **Every check in one command**: format, clippy (warnings denied), tests, build, "the window program really is a window program", version consistency, then the real-window self-test and a start-up check. `-Quick` skips the last two. |
| `scripts\release.ps1` | **Ships a release**: preconditions, `check.ps1`, push, wait for CI, tag, wait for the release build, then verify the published files (checksums, subsystems, version) and apply `docs\releases\<version>.md`. `-DryRun` stops before pushing. |
| `scripts\screenshots.ps1` | Re-shoots every image in `docs/screenshots` the same way every time (demo data, steady meters). `-Only gauge` for one. |
| `scripts\golden.ps1` | Golden screenshots for refactors that must not change the look: `-Capture <dir>`, then `-Compare <golden dir>, <new dir>` (`-Strict` also fails on the live pages). A check run freezes animation and the script parks the pointer for the run, so two captures of one build are the same picture and a diff is a real diff. `-Update <golden dir>` re-baselines deliberately and names every picture it replaced (never use it to make a failure pass). |
| `scripts\click-test.ps1` | Drives the **real window with the real mouse**: click the boost control, confirm the summary, game starts, Restore. `-Control all` for the three looks. Leave the PC alone while it runs. |
| `scripts\startup-profile.ps1` | Median start-up milestones over several launches (`CATALYX_TRACE`). |
| `scripts\footprint.ps1` | Memory and CPU of a running program (see [FOOTPRINT.md](FOOTPRINT.md)). |

## Releasing

1. Bump `version` in `Cargo.toml` and write `docs\releases\<version>.md`; commit both.
2. `.\scripts\release.ps1 -DryRun`, then `.\scripts\release.ps1`.

A pushed tag `vX.Y.Z` runs `.github/workflows/release.yml`, which builds `catalyx.exe` and `catalyx-cli.exe`
and attaches them with their SHA-256 files; the script does the waiting and the verifying.
## Regenerating assets

- **Icon:** edit the geometry in `skins/classic/src/gui/mark.rs`, build, then
  `.\target\release\catalyx.exe --write-icon assets\catalyx.ico` and build again (the build embeds the file).
- **Screenshots** in `docs/screenshots` are produced with `--screenshot` as above.
